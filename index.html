trust-center

A vendor trust center: prospects and customers browse your security and compliance documentation, but nothing is downloadable anonymously — every file is gated by a form, private files require a click-through NDA, and every request lands in an append-only ledger that already knows whether the requester is a customer or a new sales lead.

What it does

Two surfaces on one Next.js app, sharing one database.

The public trust center

  • A document library grouped by type — Policies, Procedures, Audits, Certifications, Reports, Whitepapers — each marked Public or Private by the vendor.
  • Every download is gated by a short form (name, work email, organization, country). The "whitepaper gate" pattern: nothing leaves anonymously.
  • Private files additionally require a click-through NDA — the vendor's own text or a built-in template — before the file is released. Acceptance is recorded with the signer's name, email, a SHA-256 hash of the exact NDA text, a timestamp, and the IP.

The vendor admin console

  • Document CRUD and upload; per-document public/private and NDA assignment.
  • Requests — every capture, in an append-only ledger, filterable by customer or lead, showing the matched Salesforce account or lead domain.
  • Sales leads — non-customer domains, aggregated with request counts.
  • NDA templates, users with role-based access, an audit log, and settings (SSO and security posture). Okta and Google SSO are scaffolded and auto-enable when their env vars are set.

When and where to use it

Use it when

  • Your security documentation is what prospects ask for during a deal, and you want the interest captured rather than handed out anonymously.
  • You need a defensible record of who accepted which NDA, over exactly which text, and when.
  • You want download interest to land in front of the sales team already classified as an existing customer or a fresh lead.

Do not expect

  • A CRM. It classifies a requester against a customer directory; it does not replace Salesforce — it points back at it.
  • A signed-contract workflow. The NDA is a click-through gate on a download, recorded for evidence, not a negotiated agreement.
  • Real customer data in this demo — the Salesforce directory is a seeded mock (below).

The controls that make it trustworthy

A trust center that cannot prove its own record is just a download page. The point of this one is that the evidence is enforced, not asserted.

  • Immutable ledger. DownloadRequest, NdaAcceptance and AuditLog are append-only. Postgres BEFORE UPDATE/DELETE triggers reject any mutation (error 23001), and the app connects with a least-privilege role (trust_app) that holds only INSERT/SELECT on those tables. Enforced by the database, verified by the test suite.
  • Role-based access (Owner / Admin / Viewer) enforced server-side in the admin layout and in every server action — not just hidden in the UI.
  • Gated storage. Private files live in S3 (server-side encrypted in production) and are served only through a gated, time-boxed download token — never a public object URL.
  • Audit logging of downloads, NDA acceptances, and admin changes; input validation everywhere; session hardening and security-conscious defaults.

Customer vs. lead, at the moment of interest

Each requester's email domain is matched against a Salesforce customer directory. A match classifies the request as a Customer, with the account name; no match records it as a Sales lead by domain. Both are visible to the vendor team the moment the download happens, so document interest is a signal, not an afterthought.

In this build the Salesforce directory is a seeded mock table. Going live is a matter of swapping that lookup for a real SOQL query — the classification, ledger, and admin surfaces stay the same.

How it's built

LayerChoice
AppA single Next.js app serving both the public site and the /admin console.
DataPostgres via Prisma, with the append-only triggers and least-privilege role above.
FilesS3 for document blobs in production (local disk in development), token-gated.
AuthAuth.js for admin sign-in; Okta and Google SSO scaffolded.
HostingAWS App Runner + RDS, built and shipped from a Dockerfile via CodeBuild and Terraform.

Honest limits

  • The Salesforce match is a mock directory in this demo, as noted — the one lookup you wire to go live.
  • The demo is a working trust center with seeded content; treat every document and requester in it as illustrative, not real.
  • SSO is scaffolded and off until its environment variables are supplied.
